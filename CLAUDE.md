# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal 3D portfolio: a Vite 6 single-page app in React 19 (with the React Compiler) with React Three Fiber 9 + drei 10, Tailwind 4 and framer-motion 12. Deployed to GitHub Pages at https://yel-hadr.github.io/ (the root), published into the `yel-hadr/yel-hadr.github.io` repo.

## Commands

```bash
npm run dev       # Vite dev server at http://localhost:5173/
npm run build     # production build into dist/
npm run preview   # serve dist/ locally
npm run lint      # eslint . (flat config in eslint.config.js)
npm run deploy    # predeploy runs lint + build, then gh-pages publishes dist/ to yel-hadr/yel-hadr.github.io (main)
npx eslint src/components/Hero.jsx   # lint a single file
npm run format    # prettier --write . (config: .prettierrc.json; ignores *.md, .claude, public)
npm run format:check
```

There is no test suite. Prettier style is semicolons, single quotes in JS and JSX, and 100-character lines.

## Ground rules

- **JavaScript/JSX only.** Do not introduce TypeScript (no `.ts`/`.tsx`, no type annotations) unless explicitly asked.
- **`src/constans/` is spelled that way on purpose** (legacy spelling). Do not "fix" it in passing. A rename must be its own commit that updates every import.
- **EmailJS keys come only from `VITE_EMAILJS_SERVICE_ID`, `VITE_EMAILJS_TEMPLATE_ID`, `VITE_EMAILJS_PUBLIC_KEY`** (read via `import.meta.env` in `Contact.jsx`, set in a gitignored `.env`). Never hardcode them. `VITE_*` values are inlined into the client bundle by design.
- Never hand-edit `.env*`, `package-lock.json` or `dist/`. A PreToolUse hook in `.claude/settings.json` blocks edits to `.env*` and the lockfile.

## CI/CD

`.github/workflows/deploy.yml` ("CI/CD Pipeline"), on Node 22. A concurrency group per PR (or ref) cancels a PR's superseded runs; runs on `main` are never cancelled. `lint-and-test` restores `node_modules` from the Actions cache (keyed on the Node version and `package-lock.json`; a hit skips `npm ci`), then runs `npm audit --omit=dev --audit-level=high` (a high or critical advisory in a production dependency fails it), lint, `format:check`, build and an asset-path check, and uploads `dist/`. On a PR, `lighthouse` runs `@lhci/cli` (`lighthouserc.json`) against `vite preview` of that `dist/`: the desktop preset, the median of 5 runs, and it fails below 0.9 in performance, accessibility or best practices; A second run (`lighthouserc.mobile.json`, Lighthouse's emulated low-end phone, median of 3) fails below 0.9 in accessibility or best practices; its performance below 0.9 only warns, since a continuously animated canvas and WebGL on that emulated phone stay near 0.5 (0.31 before Phase 9). Both runs' scores go to the job summary and the reports to an artifact. On a push to `main`, `deploy-to-pages` publishes that job's `dist/` artifact with `peaceiris/actions-gh-pages` to `yel-hadr/yel-hadr.github.io` (`main`), so merging to `main` deploys. `status.yml` (the status monitor, see below) publishes to the same repo every 30 minutes. It authenticates with the `ACTIONS_DEPLOY_KEY` secret (a write deploy key on that repo). The EmailJS values come from `VITE_EMAILJS_*` repo secrets. The job deploys to the `yel-hadr.github.io` environment, not `github-pages`, because that one only allows the old `gh-pages` branch. The resume is `public/Youssef_Elhadraoui_Resume.pdf`, linked through `person.resume` (built from `import.meta.env.BASE_URL`) by `ResumeLink`.

## Base path and hosting (GitHub Pages)

`vite.config.js` sets `base: '/'`: the site is a GitHub Pages *user* site, so this source repo (`yel-hadr/portfolio`) is not what Pages serves. The build is published to the `main` branch of `yel-hadr/yel-hadr.github.io`, which serves https://yel-hadr.github.io/. There is no router; in-page navigation uses `#section` anchors. Consequences:
- The dev server URL is `http://localhost:5173/`.
- Imported assets and `url()` in CSS are rewritten by Vite automatically.
- Files in `public/` (the GLB model) are referenced relatively (`./planet/scene.glb`) or via `import.meta.env.BASE_URL`, so they keep working if the base path changes again.

## Architecture

**Data-driven content.** All portfolio content (`person` (name, alias, title, summary), `navLinks`, `services`, `technologies`, `experiences`, `projects`, `education`) lives in `src/constans/index.js`. Images live in `src/assets/` and are re-exported by name from `src/assets/index.js`, which the constants file imports. Section components just map over these arrays. Adding content means asset → `assets/index.js` export → entry in `constans/index.js`. Components should not need to change. The `/add-project` skill automates this.

**Sections and landmarks.** `App.jsx` renders a skip link, `Navbar` (`<nav>`), then `<main id="main">` with Hero, About, Experience, Tech, Works, Education and Contact, then `Footer`. Each section is wrapped in `ErrorBoundary`. Sections other than Hero use the `SectionWrapper(Component, idName)` HOC (`src/hoc/sectionWrapper.jsx`). It renders `<section id={idName} aria-labelledby={`${idName}-title`}>` with shared padding and the scroll reveal. The navbar offset comes from `scroll-padding-top` on `html`, so anchors, `scrollIntoView` and keyboard focus all clear the navbar. Don't add `scroll-mt` as well, because the two add up. `html` also sets `scroll-behavior: smooth`, but only under `prefers-reduced-motion: no-preference`. `SectionHeader` (`src/components/SectionHeader.jsx`) renders the `h2` with that id. `navLinks` ids must match section ids.

**Theme (dark/light).** Every color is a CSS variable: `--c-<token>` holds "R G B" channels (so `bg-background/80` works) and `--color-glass*` / `--color-line` are full colors. `:root` is the dark theme (the default; "Midnight Obsidian": slate ground 11 14 20, frosted dark glass cards that lift by a faint inner glow along their top edge (`shadow-card` is an inset highlight, no drop shadow), pearl text, cool slate greys, electric amber 249 115 22, ice cyan 6 182 212 as `secondary` for tech and data accents) and `:root[data-theme='light']` is the light one, in `src/index.css`. An inline script in `index.html` sets `data-theme` and `lang` before the first paint (saved choice; dark by default; French if the browser is French). `ThemeProvider` (`src/theme/`, hook `useTheme` in `context.js`) persists the choice in localStorage, updates `meta[theme-color]` and adds a short `.theme-transition` cross-fade. The waves read `--c-wave-1/2/3` and `--wave-alpha`, and redraw when `data-theme` changes. Components use tokens only, never hex, and every pair must pass AA in **both** themes. Text on orange uses `text-on-primary`, button hover uses `bg-primary-hover`, and orange text uses `text-primary-400`. Light mode has its own language, not the dark one inverted: a warm off-white ground (250 247 242), cream glass (`--color-glass` 255 253 250 at 0.72), ink 26 26 46, warm stone greys, a deeper orange (232 93 4, dark text on it, hover 224 88 4) and an indigo secondary. Depth comes from tokens: `shadow-card` / `shadow-raised` / `shadow-modal` (`--shadow-*`: nothing on dark cards, which separate by hairlines; soft warm layers in light), and light mode has no glows (`--glow` is 0, used by the hero portrait's halo). `.card-glass` sets `box-shadow: var(--shadow-card)` directly rather than through the `shadow-card` utility: v4 builds that utility from its `@property`-registered `--tw-*` layers, and Chrome then rasterizes the cards' content (icon edges) differently from v3; a shadow utility on a card (`light:shadow-raised`) still replaces it, and no card carries a ring. `--c-ground` is the footer's band (a shade darker than the page in light), `--color-rule` the timeline's line, `--c-wave-1/2/3` the waves' colors (brand colors on dark, pastel peach, lavender and sky on light). `.scheme-dark` makes a dark island in either theme (it shares the dark `:root` block, so every token takes its dark value inside): the terminal's screen, and all of Game Mode (its root carries `scheme-dark` and `data-game-mode`; its portal dialogs take the class back, `GameInfo` through `dark`; its 3D colors come from `readGameTheme` in `Cub3D/gameTheme.js`, which reads the tokens from that root), so the game looks the same on the light page. Keyboard focus rings use the `focus` token (`--c-focus`: the brand orange on dark, 168 67 0 on light, which holds 3:1 even where the frosted navbar is over a dark photo). A `light:` variant (`@custom-variant` in `src/index.css`) exists for the rare element-level difference; prefer tokens. The browser `theme-color` comes from `--c-background` at runtime (ThemeProvider, `src/blog/entry.js`); only the pre-CSS inline scripts in `index.html`, `status/index.html` and `build/blog.js` hold the hexes (#050816, #faf7f2).

**i18n (EN/FR).** All user-facing text, including content, aria-labels and alt text, lives in `src/locales/<lang>/*.json`. `core.json` holds the site; `blog`, `status`, `terminal`, `diagrams` and `statuspage` are per-feature namespaces. `blog` and `status` are merged in `src/i18n/dictionaries.js`. The lazy features (terminal, diagrams) and the status page call `registerNamespace` from their own modules, so their text ships only with their code. `src/constans/index.js` keeps only language-independent data (ids, links, assets, tags). Components call `const { t, lang, setLang } = useI18n()` (from `src/i18n/context.js`); `t('works.items.iot.name', vars)` returns a string or array with `{var}` interpolation and falls back to English. Keep the en and fr key sets identical. Switching language fades `main`/`footer`/nav links out and in (`.lang-switching`), updates `<html lang>`, the title and the meta description, and fires a `site:langchange` event that makes the waves ripple.

The altitude palette reads the `--c-fdf-low/mid/high` tokens (ocean blue, cyan-green and the brand orange in the dark theme; indigo, teal and burnt crimson in the light one; every point along each gradient is at least 4.5:1 on its theme's background and glass, for 1 px lines). **Design system.** Tailwind v4, configured in CSS: there is no `tailwind.config.js` or PostCSS config (the `@tailwindcss/vite` plugin). `src/index.css` imports Tailwind with its sources listed by hand (`source(none)` + `@source` for `src/`, `build/` and `status/`), declares the tokens in `@theme inline` (each utility reads the `--c-*` channels on its own element, which is what keeps `.scheme-dark` islands dark; opacity modifiers such as `bg-background/80` become `color-mix()`), the font, the `xs` breakpoint and the Game Mode animations in `@theme`, and keeps v3's preflight defaults that v4 changed (grey default border color and placeholders, pointer cursors on buttons). `src/blog/blog.css` uses `@apply` through `@reference '../index.css'`. v4 differences to keep in mind: a plain `leading-*` now beats the line height a responsive `text-*` brings (write `sm:text-lg sm:leading-7`, as v3 behaved); two utilities that set the same property (`hidden` and `inline-flex`) resolve in a different order, so never combine them on one element; `outline-hidden` is v3's `outline-none`; `rounded-xs`/`rounded-sm` are v3's `rounded-sm`/`rounded`; a bare `outline-2` also sets the style; gradients use `bg-linear-to-*/srgb`. Tokens:
- Colors: `background`, `surface` / `surface-raised`, `foreground` / `foreground-muted`, `primary` (brand orange; `primary-400` for orange text, `primary-hover`), `on-primary`, `secondary` (violet on dark, indigo on light), `tertiary` (blue, decorative), `success` / `danger` / `info`, `glass` / `glass-strong` (translucent card fills over the waves), `line` / `line-strong`. `text` is `foreground`. Icons are inline `currentColor` SVGs in `src/components/icons.jsx`; the white image icons don't work in light mode. All text pairs meet WCAG AA. Components take colors from tokens only: Tailwind classes, or the `--color-*` variables in `src/index.css` where a library or canvas needs a string (timeline styles, `WavesBackground`). Put dark text on orange; white on orange is only 2.95:1.

**3D rendering: one Canvas, many inline Views.**
- `canvas/Scene3D.jsx` holds the single `<Canvas>`, lazily loaded by `App.jsx`: its chunk is fetched at idle (`canvas/loadScene3D.js`), and it mounts once the Tech section (the first 3D scene) is within a viewport of the screen, so creating the WebGL renderer (one long task) never delays the first paint or first input; once mounted it stays. It has with `<View.Port />`, `dpr={[1, 1.5]}` and `powerPreference: 'default'`. Its `style` is inline because R3F's own inline `position: relative` beats Tailwind classes.
- **The canvas scrolls with the page; it is not `position: fixed`.** A fixed canvas only changes when the main thread draws, while browsers scroll the page on the compositor thread. Scenes lagged their DOM boxes, and in Firefox and on touch they stayed in place until scrolling stopped. Instead the Canvas sits in an absolutely positioned layer at the top of the page (`h-[125vh]`, `will-change-transform`, `aria-hidden`, no pointer events). `ScrollSync` is a `useFrame` at priority -1, so it runs before drei's views without taking over rendering. Each rendered frame it sets `translate3d(0, scrollY, 0)`, so the compositor carries the drawn pixels with the page between frames. The extra 25vh below the viewport is overscan: a view scrolling up into the screen is already drawn. There is none above, because drei never draws a view whose bottom is above the viewport. Browsers without `overflow: clip` (Safari 15, Chrome < 90, Firefox < 81) keep a plain fixed canvas (`CLIP` in `Scene3D.jsx`). `resize={{ scroll: false }}` stops R3F's debounced re-measure on scroll. The canvas is always at the viewport's top-left when drawn, and `ScrollSync` corrects R3F's stored `size.top/left` if its first asynchronous measurement landed mid-scroll (a deep link). `App`'s root has `overflow-clip`, so the layer never makes the page longer. Don't lerp scene positions toward the scroll: drei scissors each view to its box, so any smoothing is visible lag.
- **Code splitting:** three, R3F and drei are reached only through lazy modules: `Scene3D`, `SceneViewImpl` and the scene components exported by `canvas/index.jsx`, plus the two demo dialogs and Game Mode. `vite.config.js` `manualChunks` keeps them in `vendor-three` and `vendor-r3f`, off the first paint, and the drei/three-stdlib parts only the demos use (OrbitControls, PointerLockControls, Html) in `vendor-r3f-demos`, and post-processing (Game Mode's facility only) in `vendor-postfx`. Don't import `three`, `@react-three/*` or `maath` from DOM components; route them through those lazy modules. Check `dist/index.html`: it should only `modulepreload` `vendor-react`, `vendor-motion` and the shared theme/i18n chunk (`ThemeProvider-*.js`, code shared with the `/status/` page, not extra bytes), and never `vendor-three` or `vendor-r3f`.
- Every scene is placed in the page with `<SceneView>` (`canvas/SceneView.jsx`), a drei inline `<View>` box whose children are tunnelled into the port: the 9 tech `Ball`s and the Contact `Earth`. (The hero desk model and the star field were removed when the waves background and profile photo replaced them.)
- The result is one WebGL context for the whole page (the waves are a 2D canvas). **Never add another `<Canvas>` to the page.** Add a `SceneView` instead. The one exception is the live demos and Game Mode, which each get a `<Canvas frameloop="demand" dpr={[1, 2]}>` inside their dialog. `DemoShell` and `GameMode` pause the page Canvas through `PageCanvasContext` (`useDemoCanvas`): App unmounts it while a demo is open and the demo mounts 600 ms later, after R3F has released the page's context (R3F 9 disposes the renderer and forces the context loss as soon as the unmount commits), so there is still only one WebGL context at a time. Both demo layers keep `CanvasErrorBoundary` wrappers (DemoShell, Works).
- Each scene sets its own camera with `ViewCamera`, except balls, which share the root camera.
- `frameloop` is always `demand` (the one exception is Game Mode while playing, see above). `FrameDriver` (in `Scene3D`) redraws on scroll, resize and pointer moves, and ticks ambient motion at about 30 fps. Under reduced motion it redraws only on scroll and resize. So animate with `delta` or `MathUtils.damp`, never per-frame constants. Use `usePrefersReducedMotion()`, which is live, to stop `AutoRotate` and `Float`.

**WebGL safety — must be preserved:**
- `useWebGL()` probes for **WebGL2** (three ≥ r163 is WebGL2-only). Without it (or when the lazy 3D layer later fails: renderer creation or chunk load), `App` turns `WebGLContext` off, so the 3D layer is skipped and every `SceneView` renders its static `fallback`; the content still renders, with `WebGLFallback` shown as a notice after the hero.
- `CanvasErrorBoundary` wraps the lazy 3D layer, catching a failed renderer or a failed chunk load and dropping only the 3D layer. It also wraps each `SceneView`'s lazy half (outer, for a chunk failure) and every scene (inner, inside `SceneViewImpl`). Inside the Canvas it renders `fallback ?? null`; DOM can't render there. `onError` makes the `SceneView` swap to its DOM `fallback` prop. `sectionType` is only a log label. Never remove these wrappers.
- Boundaries do **not** catch `useFrame` exceptions or context loss. Keep `useFrame` callbacks null-safe. A context restore triggers `invalidate()` via `onCreated`.

**GPU resources.** `useGLTF` / `useTexture` results are cached and shared. **Clone a cached scene per mount** (`Earth` does `scene.clone()`), because an Object3D has one parent. **Never dispose cached geometry, materials or textures** on unmount; the old `useCleanup` hook did, which blanked the Contact globe, and it was removed. R3F disposes the objects it creates declaratively.

**Models** are meshopt-compressed GLBs with WebP textures in `public/planet/scene.glb`. They're loaded with `useGLTF` + `useGLTF.preload`; drei's bundled MeshoptDecoder means no CDN decoder is needed. Keep each folder's `license.txt` (Sketchfab attribution). To regenerate from a source gltf, run:
`npx --yes @gltf-transform/cli@4.5.1 optimize <in>.gltf <out>.glb --compress meshopt --texture-compress webp --texture-size 1024 --simplify false`
Leave `--simplify false`: simplify removes a third of the triangles to save only about 120 KB.

## React 19 and the React Compiler

- `babel-plugin-react-compiler` (target 19, in `vite.config.js`) memoizes every component and hook it can prove pure, so those need no hand-written `useMemo`/`useCallback` (App, the theme and i18n providers, `useModalDialog`, the diagrams have none). It skips components that read refs during render or mutate values the frame loop owns (Game Mode, the demos, the terminal, Packet Snake): those keep their manual memoization, and so does every `useMemo` that keeps a three.js object alive (a clone, geometry, materials), since a memo cache is not a lifetime guarantee.
- The compiler turns a callback's property reads into memo dependencies it evaluates during render: inside a callback, read a property of a value that can be `null` with `?.` (`running?.opener`), or the render throws.
- `src/main.jsx` renders the root inside `startTransition`, so the first render yields to the browser instead of running as one long task.
- The contact form (`ContactForm.jsx`) is a form action: `useActionState` runs the EmailJS send and holds its result, `useFormStatus` gives the submit button its pending label and `aria-disabled`; the fields stay controlled (a failed send keeps them, a sent one clears them), and a submit while one is pending is ignored.
- The Ctrl+` listener reads the latest state through `useEffectEvent`.
