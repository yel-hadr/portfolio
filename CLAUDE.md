# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal 3D portfolio: a Vite 6 single-page app in React 19 (with the React Compiler) with React Three Fiber 9 + drei 10, Tailwind 4 and framer-motion 12. Deployed to GitHub Pages at https://yel-hadr.github.io/ (the root), published into the `yel-hadr/yel-hadr.github.io` repo.

## Commands

```bash
npm run dev       # Vite dev server at http://localhost:5173/
npm run build     # production build into dist/
npm run preview   # serve dist/ locally
npm run lint      # eslint . (flat config in eslint.config.js)
npm run deploy    # predeploy runs lint + build, then gh-pages publishes dist/ to yel-hadr/yel-hadr.github.io (main)
npx eslint src/components/Hero.jsx   # lint a single file
npm run format    # prettier --write . (config: .prettierrc.json; ignores *.md, .claude, public)
npm run format:check
npm run compiler:report   # lists any component or hook the React Compiler skips, and why (exits 1 if one is)
```

There is no test suite for the site itself; `contact-api/` has its own (`cd contact-api && npm test`, `node --test`), and CI runs it. Prettier style is semicolons, single quotes in JS and JSX, and 100-character lines.

## Ground rules

- **JavaScript/JSX only.** Do not introduce TypeScript (no `.ts`/`.tsx`, no type annotations) unless explicitly asked.
- **`src/constans/` is spelled that way on purpose** (legacy spelling). Do not "fix" it in passing. A rename must be its own commit that updates every import.
- **The Resend API key never touches the site.** The contact form posts to `contact-api/` (a separate Vercel project, one function: `api/contact.js`, logic in `lib/contact.js`, the email's HTML and text layout in `lib/email.js` (inline styles and the light theme's colors as hex, since email clients ignore CSS variables; every typed value escaped), a send that throws (the network to Resend down) answers 502 `{ error: 'send', reason: 'network' }` instead of an unhandled error, best-effort in-memory rate limits in `lib/rateLimit.js` (5 per client per 10 minutes, 30 an hour in all, 429 with `Retry-After`; a Vercel Firewall rule is the durable layer), tests in `test/`), which holds `RESEND_API_KEY` in Vercel's environment. The site only reads the function's public URL from `VITE_CONTACT_ENDPOINT` (`import.meta.env` in `ContactForm.jsx`; a repository *variable* in CI, `.env` locally). `VITE_*` values are inlined into the client bundle, so never give a secret a `VITE_` name or hardcode one. The form's limits (`MAX`) match the function's (`LIMITS`), and its hidden `website` field is a bot trap the function drops.
- Never hand-edit `.env*`, `package-lock.json` or `dist/`. A PreToolUse hook in `.claude/settings.json` blocks edits to `.env*` and the lockfile.

## CI/CD

`.github/workflows/deploy.yml` ("CI/CD Pipeline"), on Node 22. A concurrency group per PR (or ref) cancels a PR's superseded runs; runs on `main` are never cancelled. `lint-and-test` restores `node_modules` from the Actions cache (keyed on the Node version and `package-lock.json`; a hit skips `npm ci`), then runs `npm audit --omit=dev --audit-level=high` (a high or critical advisory in a production dependency fails it), lint, `format:check`, the contact endpoint's own `npm ci`, audit and tests (`contact-api/`), build and an asset-path check, and uploads `dist/`. On a PR, `lighthouse` runs `@lhci/cli` (`lighthouserc.json`) against `vite preview` of that `dist/`: the desktop preset, the median of 5 runs, and it fails below 0.9 in performance, accessibility or best practices; a second run (`lighthouserc.mobile.json`, Lighthouse's emulated low-end phone, median of 3) fails below 0.9 in accessibility or best practices; its performance below 0.9 only warns, since a continuously animated canvas and WebGL on that emulated phone stay near 0.5 (0.31 before Phase 9). Both runs' scores go to the job summary and the reports to an artifact. On a push to `main` (or a manual run), `deploy-contact-api` deploys `contact-api/` to Vercel with the `VERCEL_TOKEN`, `RESEND_API_KEY` and `CONTACT_TO` secrets (it only leaves a notice without the token), checks the endpoint's preflight and warns while the `VITE_CONTACT_ENDPOINT` variable differs from its URL. On a push to `main`, `deploy-to-pages` publishes that job's `dist/` artifact with `peaceiris/actions-gh-pages` to `yel-hadr/yel-hadr.github.io` (`main`), so merging to `main` deploys. `status.yml` (the status monitor, see below) publishes to the same repo every 30 minutes. It authenticates with the `ACTIONS_DEPLOY_KEY` secret (a write deploy key on that repo). The contact endpoint's URL comes from the `VITE_CONTACT_ENDPOINT` repo variable (the endpoint itself deploys on Vercel, not here). The job deploys to the `yel-hadr.github.io` environment, not `github-pages`, because that one only allows the old `gh-pages` branch. The resume is `public/Youssef_Elhadraoui_Resume.pdf`, linked through `person.resume` (built from `import.meta.env.BASE_URL`) by `ResumeLink`.

## Base path and hosting (GitHub Pages)

`vite.config.js` sets `base: '/'`: the site is a GitHub Pages *user* site, so this source repo (`yel-hadr/portfolio`) is not what Pages serves. The build is published to the `main` branch of `yel-hadr/yel-hadr.github.io`, which serves https://yel-hadr.github.io/. There is no router; in-page navigation uses `#section` anchors. Consequences:
- The dev server URL is `http://localhost:5173/`.
- Imported assets and `url()` in CSS are rewritten by Vite automatically.
- Files in `public/` (the GLB model) are referenced relatively (`./planet/scene.glb`) or via `import.meta.env.BASE_URL`, so they keep working if the base path changes again.

## Architecture

**Data-driven content.** All portfolio content (`person` (name, alias, title, summary, email, links), `navLinks`, `services`, `technologies`, `experiences`, `projects`, `education`) lives in `src/constans/index.js`; the words live in the locales (`education.items.<id>` holds the school's name too, since French writes it differently). Education is one entry, 1337 / UM6P (42 Network), RNCP Level 7, 2022 – 2027 (expected), as on the resume; the Education section, the terminal's `education` command and Game Mode's dossier all render that one list. The email (`person.email`) is a visible `mailto:` link under the Contact heading and in the footer, besides the form. Images live in `src/assets/` and are re-exported by name from `src/assets/index.js`, which the constants file imports. Section components just map over these arrays. A project tag is a product name (`name`, shown as written, `lang='en'`) or a technique (`id`, translated through `works.tags.<id>` by `tagName` in `i18n/context.js`, as Raycasting and Isometric projection are). Adding content means asset → `assets/index.js` export → entry in `constans/index.js`. Components should not need to change. The `/add-project` skill automates this.

**Sections and landmarks.** `App.jsx` renders a skip link, `Navbar` (`<nav aria-label="Main">`, announced "Main navigation": the owner kept the short name. A floating `rounded-full` pill 0.75rem from the top and sides, glass at 80% (`bg-background/80`, both themes) with `backdrop-blur-xl` and the page's film grain inside it (`.grain`, clipped to the pill), so it reads as frosted glass. Its edge (`--color-nav-edge`: white 8% on dark, black 6% on light, with the dark top highlight and the light soft shadow) is invisible at the top of the page, melting into the hero, and fades in over 300 ms once the page has scrolled 10px (`useNavScroll`, one rAF-throttled passive listener). Scrolling down past 120px slides the pill away (a `translate` on the pill, never on `<nav>`, which would become the containing block of anything fixed inside it); any scroll up brings it back. It never hides under reduced motion, with focus inside it (WCAG 2.4.11), with the sheet open, or for 1.5 s after a jump from its own links (that smooth scroll goes down by itself). The links sit in a recessed track, and the current one stands on a pill (`m.li`, with a `line-strong` ring so the mark is more than color) whose `x` and width spring to the link's measured box (`usePillPosition`, re-measured by a ResizeObserver): the look of a `layoutId` indicator without framer's layout bundle, which the owner chose to keep off the first paint. Below `lg` the links live in a bottom sheet (`MobileSheet`, portaled into `<body>` on `useModalDialog`: page inert, Tab trapped, Escape and a backdrop tap close it and focus returns to the menu button; a link moves focus to its section instead). It springs up from the bottom over an 8px-blurred backdrop and slides back down before it unmounts; rows are 52px, the current one filled with an orange bar on its edge. The theme and pause toggles morph between their two icons (`.icon-swap` in index.css: rotation and scale with a spring-like overshoot, more specific than `.theme-transition` so the theme's cross-fade does not freeze it); the pressed pause toggle turns orange inside an orange ring with a faint glow (dark only). Icon buttons lift to 1.05 on hover (200 ms). The bar is outside the content's `z-10` wrapper, so it stays above the 3D layer), then `<main id="main">` with Hero, About, Experience, Tech, Works, Education, Blog and Contact, then `Footer`. Each section is wrapped in `ErrorBoundary`. Only the navbar and Hero are in the main chunk: the sections below the hero are one lazy chunk (`BelowFold.jsx`) and the footer another, both requested with the first render, so a phone's first paint waits on less JavaScript. A `#section` link arrives before its section exists, so `BelowFold` follows the hash again once it mounts, and moves focus to the section as a nav click does (so Tab continues from there). Components are imported by their own paths: there is no `./components` barrel, since one would pull every section back into the main chunk. Sections other than Hero use the `SectionWrapper(Component, idName)` HOC (`src/hoc/sectionWrapper.jsx`). It renders `<section id={idName} aria-labelledby={`${idName}-title`}>` with shared padding and the scroll reveal. The navbar offset comes from `scroll-padding-top` on `html`, so anchors, `scrollIntoView` and keyboard focus all clear the navbar. Don't add `scroll-mt` as well, because the two add up. `html` also sets `scroll-behavior: smooth`, but only under `prefers-reduced-motion: no-preference`. `SectionHeader` (`src/components/SectionHeader.jsx`) renders the `h2` with that id, under the section's eyebrow (`eyebrows.<id>` in core.json: one short uppercase label, `styles.eyebrow`, that adds to the heading rather than repeating it: "Toolbox" over "Tech stack.", "Peer learning" over "Education."). `navLinks` ids must match section ids.

**Theme (dark/light).** Every color is a CSS variable: `--c-<token>` holds "R G B" channels (so `bg-background/80` works) and `--color-glass*` / `--color-line` are full colors. `:root` is the dark theme (the default; "Midnight Obsidian": slate ground 11 14 20, frosted dark glass cards that lift by a faint inner glow along their top edge (`shadow-card` is an inset highlight, no drop shadow), pearl text, cool slate greys, electric amber 249 115 22, ice cyan 6 182 212 as `secondary` for tech and data accents) and `:root[data-theme='light']` is the light one, in `src/index.css`. An inline script in `index.html` sets `data-theme` and `lang` before the first paint (saved choice; dark by default; French if the browser is French). Dark by default regardless of `prefers-color-scheme` is the owner's deliberate choice: don't flag it in audits. `ThemeProvider` (`src/theme/`, hook `useTheme` in `context.js`) persists the choice in localStorage, updates `meta[theme-color]` and adds a short `.theme-transition` cross-fade. The waves read `--c-wave-1/2/3` and `--wave-alpha`, and redraw when `data-theme` changes. Components use tokens only, never hex, and every pair must pass AA in **both** themes. Text on orange uses `text-on-primary`, button hover uses `bg-primary-hover`, and orange text uses `text-primary-400`. Light mode has its own language, not the dark one inverted: a warm off-white ground (250 247 242), warm-white cards (`--color-glass` 255 254 252 at 0.88, rendering about #FEFDFB) edged by an ink hairline (26 26 46 at 0.07, 0.11 under the pointer) over three soft warm shadow layers (`--shadow-card`, deepening to `--shadow-card-hover` as the card lifts 2px: `--card-lift`, through `translate` so framer's inline transform does not override it; `FrameDriver` redraws the 3D layer every frame while a `translate` transition runs, so a bento ball keeps to its lifting card even with the ambient ticks off), orange eyebrows (`--c-eyebrow` 168 67 0), a primary button with a lit top edge (white 40%) over a soft drop shadow, a grain in `overlay` at 0.045 (`--grain-blend`: matte paper without greying the ground) and a white gloss in place of the rim light (`--spot-rim` 0, `--spot-fill` 0.4), ink 26 26 46, warm stone greys, a deeper orange (232 93 4, dark text on it, hover 224 88 4) and an indigo secondary. Depth comes from tokens: `shadow-card` / `shadow-raised` / `shadow-modal` (`--shadow-*`: nothing on dark cards, which separate by hairlines; soft warm layers in light), and light mode has no glows (`--glow` is 0, used by the hero portrait's halo). `.card-glass` sets `box-shadow: var(--shadow-card)` directly rather than through the `shadow-card` utility: v4 builds that utility from its `@property`-registered `--tw-*` layers, and Chrome then rasterizes the cards' content (icon edges) differently from v3; a shadow utility on a card (`light:shadow-raised`) still replaces it, and no card carries a ring. `--c-ground` is the footer's band (a shade darker than the page in light), `--color-rule` the timeline's line, `--c-wave-1/2/3` the waves' colors (brand colors on dark, pastel peach, lavender and sky on light). `.scheme-dark` makes a dark island in either theme (it shares the dark `:root` block, so every token takes its dark value inside): the terminal's screen, and all of Game Mode (its root carries `scheme-dark` and `data-game-mode`; its portal dialogs take the class back, `GameInfo` through `dark`; its 3D colors come from `readGameTheme` in `Cub3D/gameTheme.js`, which reads the tokens from that root), so the game looks the same on the light page. Keyboard focus rings use the `focus` token (`--c-focus`: the brand orange on dark, 168 67 0 on light, which holds 3:1 even where the frosted navbar is over a dark photo). A `light:` variant (`@custom-variant` in `src/index.css`) exists for the rare element-level difference; prefer tokens. The browser `theme-color` comes from `--c-background` at runtime (ThemeProvider, `src/blog/entry.js`); only the pre-CSS inline scripts in `index.html`, `status/index.html` and `build/blog.js` hold the hexes (#0b0e14, #faf7f2).

**i18n (EN/FR).** All user-facing text, including content, aria-labels and alt text, lives in `src/locales/<lang>/*.json`. `core.json` holds the site; `blog`, `status`, `terminal`, `diagrams`, `games`, `demos` and `statuspage` are per-feature namespaces. `blog` and `status` are merged in `src/i18n/dictionaries.js`. The lazy features (terminal, diagrams) and the status page call `registerNamespace` from their own modules, so their text ships only with their code. `src/constans/index.js` keeps only language-independent data (ids, links, assets, tags). Components call `const { t, lang, setLang } = useI18n()` (from `src/i18n/context.js`); `t('works.items.iot.name', vars)` returns a string or array with `{var}` interpolation and falls back to English. Keep the en and fr key sets identical. Switching language fades `main`/`footer`/nav links out and in (`.lang-switching`), updates `<html lang>`, the title and the meta description, and fires a `site:langchange` event that makes the waves ripple.

**3D rendering: one Canvas, many inline Views.**
- `canvas/Scene3D.jsx` holds the single `<Canvas>`, lazily loaded by `App.jsx`: its chunk is prefetched once the page has settled (`afterSettle` in `src/utils/afterSettle.js`: after `load`, 3 s, then idle time; the terminal chunk too), and it mounts once the Tech section (the first 3D scene) is within a viewport of the screen, so creating the WebGL renderer (one long task) never delays the first paint or first input; once mounted it stays. It has `<View.Port />`, `dpr={[1, 1.5]}`, `powerPreference: 'default'` and `alpha: true` with `premultipliedAlpha: false` (the owner's choice; the demos and Game Mode use the same; measured: no seam against either theme's background, no edge fringes). Its `style` is inline because R3F's own inline `position: relative` beats Tailwind classes.
- **The canvas scrolls with the page; it is not `position: fixed`.** A fixed canvas only changes when the main thread draws, while browsers scroll the page on the compositor thread. Scenes lagged their DOM boxes, and in Firefox and on touch they stayed in place until scrolling stopped. Instead the Canvas sits in an absolutely positioned layer at the top of the page (`h-[125vh]`, `will-change-transform`, `aria-hidden`, no pointer events). The layer is `z-20`, above the content's `z-10` (the balls sit inside the bento's glass cards, whose fill and blur would cover them) and below the navbar; it draws only inside each view's box. `ScrollSync` is a `useFrame` at priority -1, so it runs before drei's views without taking over rendering. Each rendered frame it sets `translate3d(0, scrollY, 0)`, so the compositor carries the drawn pixels with the page between frames. The extra 25vh below the viewport is overscan: a view scrolling up into the screen is already drawn. There is none above, because drei never draws a view whose bottom is above the viewport. Browsers without `overflow: clip` (Safari 15, Chrome < 90, Firefox < 81) keep a plain fixed canvas (`CLIP` in `Scene3D.jsx`). `resize={{ scroll: false }}` stops R3F's debounced re-measure on scroll. The canvas is always at the viewport's top-left when drawn, and `ScrollSync` corrects R3F's stored `size.top/left` if its first asynchronous measurement landed mid-scroll (a deep link). `App`'s root has `overflow-clip`, so the layer never makes the page longer. Don't lerp scene positions toward the scroll: drei scissors each view to its box, so any smoothing is visible lag.
- **Code splitting:** three, R3F and drei are reached only through lazy modules: `Scene3D`, `SceneViewImpl` and the scene components exported by `canvas/index.jsx`, plus the two demo dialogs and Game Mode. `vite.config.js` `manualChunks` keeps them in `vendor-three` and `vendor-r3f`, off the first paint, and the drei/three-stdlib parts only the demos use (OrbitControls, PointerLockControls, Html) in `vendor-r3f-demos`, and post-processing (Game Mode's facility only) in `vendor-postfx`. Don't import `three`, `@react-three/*` or `maath` from DOM components; route them through those lazy modules. Until the 3D layer mounts, `Near3DContext` (false) keeps every `SceneView` an empty box, so its lazy `SceneViewImpl` (and three.js with it) is not requested while the page is still loading: Lighthouse counts every request and task before LCP, and fetching three.js early held phone LCP back by about 1.5 s. Images are never inlined as base64 (`assetsInlineLimit` in `vite.config.js`): `constans` imports every icon and the first-paint chunk imports `constans`, so inlined icons put about 30 kB of base64 on the first paint (main was 38 kB gzipped, 16 kB without them). Helpers only lazy code uses (`classnames`, `prop-types`, `react-intersection-observer`, `use-sync-external-store`) are `vendor-shared`, not `vendor-react`. First paint is about 138 kB of JS and CSS gzipped. Check `dist/index.html`: it should only `modulepreload` `vendor-react`, `vendor-motion` and the shared theme/i18n chunk (`ThemeProvider-*.js`, code shared with the `/status/` page, not extra bytes), and never `vendor-three` or `vendor-r3f`.
- Every scene is placed in the page with `<SceneView>` (`canvas/SceneView.jsx`), a drei inline `<View>` box whose children are tunnelled into the port: the 12 tech `Ball`s and the Contact `Earth`. `className` sizes SceneView's outer box, which stays one element through its states for two IntersectionObservers: the scene mounts (and fetches its model) only once the box is within a viewport of the screen, so the globe's 480 KB GLB waits for Contact rather than for Tech; and while a mounted box is on screen (or in the 25vh overscan) it counts in `viewPresence.js`, which `FrameDriver` reads to tick ambient motion only while some 3D view is in sight. (The hero desk model and the star field were removed when the waves background and profile photo replaced them.)
- The result is one WebGL context for the whole page (the waves are a 2D canvas). **Never add another `<Canvas>` to the page.** Add a `SceneView` instead. The one exception is the live demos and Game Mode, which each get a `<Canvas frameloop="demand" dpr={[1, 2]}>` inside their dialog. `DemoShell` and `GameMode` pause the page Canvas through `PageCanvasContext` (`useDemoCanvas`): App unmounts it while a demo is open and the demo mounts 600 ms later, after R3F has released the page's context (R3F 9 disposes the renderer and forces the context loss as soon as the unmount commits), so there is still only one WebGL context at a time. Both demo layers keep `CanvasErrorBoundary` wrappers (DemoShell, Works).
- Each scene sets its own camera with `ViewCamera`, except balls, which share the root camera.
- `frameloop` is always `demand` (the one exception is Game Mode while playing, see above). `FrameDriver` (in `Scene3D`) redraws on scroll and resize, and ticks ambient motion at about 30 fps; no scene follows the pointer, so pointer moves draw nothing (they used to redraw at the display's rate for a hero parallax that is gone). Under reduced motion, or with the navbar's pause switch on, it redraws only on scroll and resize. So animate with `delta` or `MathUtils.damp`, never per-frame constants. Use `usePrefersReducedMotion()`, which is live, to stop `AutoRotate` and `Float`.

**WebGL safety — must be preserved:**
- `useWebGL()` probes for **WebGL2** (three ≥ r163 is WebGL2-only). Without it (or when the lazy 3D layer later fails: renderer creation or chunk load), `App` turns `WebGLContext` off, so the 3D layer is skipped and every `SceneView` renders its static `fallback`; the content still renders, with `WebGLFallback` shown as a notice after the hero.
- `CanvasErrorBoundary` wraps the lazy 3D layer, catching a failed renderer or a failed chunk load and dropping only the 3D layer. It also wraps each `SceneView`'s lazy half (outer, for a chunk failure) and every scene (inner, inside `SceneViewImpl`). Inside the Canvas it renders `fallback ?? null`; DOM can't render there. `onError` makes the `SceneView` swap to its DOM `fallback` prop. `sectionType` is only a log label. Never remove these wrappers.
- Boundaries do **not** catch `useFrame` exceptions or context loss. Keep `useFrame` callbacks null-safe. A context restore triggers `invalidate()` via `onCreated`.

**GPU resources.** `useGLTF` / `useTexture` results are cached and shared. **Clone a cached scene per mount** (`Earth` does `scene.clone()`), because an Object3D has one parent. **Never dispose cached geometry, materials or textures** on unmount; the old `useCleanup` hook did, which blanked the Contact globe, and it was removed. The one exception is Game Mode's layer, whose renderer goes with it: its module-level shapes (`SHAPES`, `VOXEL`, `freeShared`) and its cached icon textures are disposed on unmount. That frees the dead renderer's GPU copies and the dispose listener that otherwise kept every old renderer reachable, and the next world's renderer uploads them again. R3F disposes the objects it creates declaratively.

**Models** are meshopt-compressed GLBs with WebP textures in `public/planet/scene.glb`. They're loaded with `useGLTF` + `useGLTF.preload`; drei's bundled MeshoptDecoder means no CDN decoder is needed. Keep each folder's `license.txt` (Sketchfab attribution). To regenerate from a source gltf, run:
`npx --yes @gltf-transform/cli@4.5.1 optimize <in>.gltf <out>.glb --compress meshopt --texture-compress webp --texture-size 1024 --simplify false`
Leave `--simplify false`: simplify removes a third of the triangles to save only about 120 KB.

## React 19 and the React Compiler

- `babel-plugin-react-compiler` (target 19, in `vite.config.js`) memoizes every component and hook it can prove pure, so those need no hand-written `useMemo`/`useCallback` (App, the theme and i18n providers, `useModalDialog`, the diagrams have none). It compiles all of them, Game Mode, the demos, the terminal and Packet Snake included; `npm run compiler:report` must keep saying "Skipped: none" (a skipped component falls back to plain React silently). The manual memoization that remains is kept on purpose: every `useMemo` that keeps a three.js object alive (a clone, geometry, materials), since a memo cache is not a lifetime guarantee, and the stable handlers drei's controls and the memoized `Scene`/`GameLayer` need. What makes the compiler skip a component, and the way around it here:
  - An `eslint-disable` of a `react-hooks` rule anywhere in it: read the values an effect must not re-run for through `useEffectEvent` instead.
  - Reading or writing a ref's `current` during render: set a latest-value ref in a layout effect (`useLiveRef`, `src/hooks/useLiveRef.js`, or a dependency-free `useLayoutEffect` for a handler), and keep what render shows in state (MISSION COMPLETE takes a snapshot of the time and shots as state; `GameMode`'s demo return point is state).
  - Assigning to a value a hook returned (a `useMemo`'d three.js material, R3F's `camera` or `scene` from `useThree`, even useFrame's `state.camera`): the frame loop reaches those through a ref (`useLiveRef(materials)`, `useLiveRef(camera)`), effects through `useThree((s) => s.get)()`. Method calls (`position.set`) are allowed; property assignments are not.
  - A ref passed as a prop and written to: name the prop `…Ref` (`motionRef`, `postFxRef`, `slowRef`), so the compiler knows it for a ref.
  - A value used before its declaration in a hook's callback (a ref declared below the `useCallback` that reads it): declare it first.
  - `??=`, `||=`, a dynamic `import()`, or a conditional expression inside `try`, in a component: plain assignments, and module-level helpers (`loadSfx`, `saveSetting`).
  - `Date.now()`/`performance.now()` in a handler the compiler cannot tell from render code: a module-level clock (`timeNow`, `clock`).
  - A manual `useCallback` it cannot preserve (reported as "Existing memoization could not be preserved"): move the work that blocks it out of the callback (`onLockChange` sets state; an effect on `locked` does the focus).
- The compiler turns a callback's property reads into memo dependencies it evaluates during render: inside a callback, read a property of a value that can be `null` with `?.` (`running?.opener`), or the render throws.
- `src/main.jsx` renders the root inside `startTransition`, so the first render yields to the browser instead of running as one long task.
- The contact form (`ContactForm.jsx`) is a form action: `useActionState` runs the send to the contact endpoint and holds its result, `useFormStatus` gives the submit button its pending label and `aria-disabled`; the fields stay controlled (a failed send keeps them, a sent one clears them), and a submit while one is pending is ignored. It validates itself (`noValidate`, so no browser popups, which speak the browser's language rather than the page's): a missing or malformed field gets a message under it (`contact.errors.*`, kept as a key so it follows a language switch), `aria-invalid` and a red border, and the first one takes focus; a marked field is checked again as it is typed in.
- The Ctrl+` listener reads the latest state through `useEffectEvent`.
